# Luxury House — калькулятор модульных домов

Рабочая система расчёта модульных домов для производителя Luxury House: геометрия и
комплектация → материалы и труд → себестоимость → цена → клиентская смета и
производственное задание. Три роли (Цех/Менеджер/Владелец) с реальным разграничением прав
на уровне API, не только интерфейса.

Реализовано по единому промпту `Luxury_House_Calculator_Complete.md`. Архив с исходными PDF,
`data/*.json` и изображениями планировок в этой среде приложен **не был** — только сам
Markdown-документ. Файлы `data/*.json` в этом репозитории воссозданы из числовых данных,
буквально приведённых в тексте задания (Приложения А–Г), а не скопированы из оригинального
архива. Это открыто помечено в самих файлах (`sourceFileAvailable: false` у каждого проекта
каталога) и подробно объяснено в разделе «Честные ограничения» ниже.

## Архитектура

```
calc-engine/   Чистое расчётное ядро (TypeScript + decimal.js), не зависит от UI/БД.
               Формулы окон, свай, раскроя, труда, накладных, цены, опций, реальной
               геометрии стен/кровли (shell.ts: периметр, площадь ската по 9°, вычет
               проёмов). 57 автотестов, многие — прямые контрольные примеры раздела 23 ТЗ.

server/        Express + TypeScript + Prisma (SQLite) + JWT-аутентификация.
               Оркестратор сметы (buildEstimate) соединяет calc-engine с данными проекта.
               Ролевая проекция ответа (roleViews.ts) — единая точка, где Цех и Менеджер
               физически не получают закупочные цены/себестоимость в JSON.
               Экспорты: XLSX (владелец), клиентские PDF/DOCX, производственный XLSX (цех).
               Импорт PDF: реальное извлечение текста (pdfjs-dist) + классификация страниц.

client/        React + Vite + TypeScript. Три представления в одном приложении,
               определяются ролью из JWT, а не переключателем на клиенте.

data/          project_catalog.json (13 планировок), window_catalog.json, 
               calculation_defaults.json (тарифы/нормы), reference_tables.json (реестр
               для нормализации). Все — редактируемые исходные записи, не «зашитые» цены.
```

### Почему такой стек

- **TypeScript везде** — единая модель типов между ядром, сервером и клиентом, важно для
  точного соответствия формулам ТЗ без рассинхронизации типов на границах.
- **Decimal.js** в расчётном ядре — деньги и коэффициенты считаются точной десятичной
  арифметикой (раздел 22: «не рассчитывай итог через округлённую экранную цену»).
- **SQLite через Prisma** — работает без внешней СУБД, что упрощает запуск в любой среде;
  схема переносится на PostgreSQL заменой одной строки `datasource`, если потребуется рост.
- **pdfjs-dist** — реальный, а не имитационный разбор PDF (см. ограничения ниже).
- **Playwright/Chromium не использован для PDF** — вместо него взят `pdfkit` с внедрённым
  шрифтом DejaVuSans (кириллица), т.к. он проще для серверной генерации документов без
  браузерного рендеринга HTML.

## Запуск

```bash
npm install                      # из корня — поднимет все три workspace

# Сервер
cd server
cp .env.example .env             # при необходимости поменяйте JWT_SECRET
npx prisma db push               # создаст server/prisma/dev.db (SQLite)
npm run seed                     # создаст 3 демо-аккаунта (owner/manager/workshop)
npm run dev                      # http://localhost:4000

# Клиент (в отдельном терминале)
cd client
npm run dev                      # http://localhost:5173, проксирует /api на :4000
```

Демо-доступы (пароли — тестовые, сменить перед реальным использованием):

| Роль | Email | Пароль |
|---|---|---|
| Владелец | owner@demo.luxuryhouse.local | owner-demo-pass |
| Менеджер | manager@demo.luxuryhouse.local | manager-demo-pass |
| Цех | workshop@demo.luxuryhouse.local | workshop-demo-pass |

### Тесты

```bash
cd calc-engine && npx vitest run   # 57 тестов — формулы окон/свай/раскроя/труда/цены/геометрии
cd server && npx vitest run        # 8 тестов — оркестратор сметы + реальное извлечение PDF
```

## Что реально работает (проверено вручную через браузер и curl)

- Вход по email/паролю, роль хранится на сервере в JWT, а не в localStorage-флаге.
- Менеджер создаёт проект из 13 стартовых планировок, настраивает окна (точный расчёт по
  каталогу W1–W4/D1 или предварительная оценка при изменении размера — раздел 11.3),
  опции, схему фундамента, режим цены — и получает реальный расчёт от расчётного ядра.
- Владелец видит полную себестоимость, резерв, накладные, прибыль, наценку, маржу и все
  четыре экспорта; Менеджер — только рекомендованную/минимальную цену и клиентские
  экспорты; Цех — только состав и статусы, без единой суммы в рублях.
- **Разграничение прав проверено не только через UI, но и прямыми HTTP-запросами** —
  в процессе разработки так была найдена и исправлена реальная утечка (см. ниже).
- Экспорты реально генерируются и скачиваются: XLSX (ExcelJS), PDF и DOCX с кириллицей.
- Загрузка PDF реально извлекает текст постранично через `pdfjs-dist`, классифицирует
  страницы по ключевым словам и находит числа-кандидаты на размеры — проверено
  синтетическим тестовым чертежом (см. `server/test/pdfImport.test.ts`).
- Учёт факта цехом с идемпотентным ключом (повторная отправка не создаёт вторую запись).
- Версионирование: пересчёт создаёт новую версию сметы, старые снимки не переписываются.

## Найденные и исправленные в процессе баги (для прозрачности)

1. **Утечка себестоимости менеджеру.** Первая версия API возвращала сырой объект
   `EstimateSnapshot` из Prisma (включая нередактированный `resultJson` со всеми
   закупочными ценами) рядом с уже отфильтрованным полем `estimate`. Исправлено —
   наружу теперь уходит только `{id, version, createdAt}`. Обнаружено собственным
   контрольным скриптом, не оставлено «на потом».
2. **Сброс роли при обновлении страницы.** JWT кодируется в base64url (`-`/`_`, без
   `=`-паддинга), а клиент декодировал его обычным `atob()` — при прямом заходе по
   ссылке или F5 пользователя молча выбрасывало на экран входа. Исправлено правильным
   base64url-декодированием.
3. **Кириллица в имени пользователя ломалась** после того же декодирования — `atob()`
   даёт байтовую строку, для UTF-8 после него нужен `TextDecoder`. Исправлено.

Все три найдены и закрыты сквозным браузерным тестом (Playwright + headless Chromium) в
рамках этой же сессии, не после сдачи.

## Углубление: реальная геометрия вместо коэффициента ₽/м² (раздел 7)

Первая версия считала «дом без отделки» одним маштабированным по площади числом. Это
прямо противоречит разделу 7.1 ТЗ («нельзя хранить весь дом одним коэффициентом ₽/м²»).
Доработка:

- В `data/project_catalog.json` для 11 из 13 планировок добавлен `rectFootprint`
  (пролёт/длина закрытого прямоугольного контура), выведенный из текста ТЗ по правилу
  «общая с террасой сторона = пролёт кровли» (сверено на Барне 96, где пролёт 8 м явно
  подтверждён примером раздела 7.2) — с явным полем `confidence`, показывающим, откуда
  взято число: `confirmed_by_example` / `confirmed_by_shared_dimension` /
  `inferred_by_family_pattern` / `assumed`.
- `calc-engine/src/shell.ts` — периметр, площадь стен, площадь ската (двускатная 9° для
  Барна), вычет проёмов, объём утеплителя. Новые тесты сверяют площадь стен Барна 96
  (34 м периметр × 2,37 м = 80,58 м²) и подъём конька (0,6335 м) с текстом ТЗ.
- `server/.../buildEstimate.ts` теперь считает для каждого дома с прямоугольным контуром:
  чистую площадь стен (за вычетом реально выбранных окон), наружную облицовку планкеном,
  утеплитель Knauf (стены+пол), кровельный профлист, Изоспан А (стены) и АМ (кровля) —
  каждая строка своим количеством и ценой из `calculation_defaults.json`, а не одной
  аналоговой суммой. Каркас/крепёж/работы по сборке остаются аналогом (для них по-прежнему
  нет ни чертежа, ни нормы на узел — раздел 7.5 уровень 3 применяется честно).
- Проверено вживую: создание проекта «Барн 96» в браузере, добавление окна W1 — площадь
  стен в интерфейсе меняется с 80,58 до 75,96 м² (минус 2,1×2,2 м проёма), в точности как
  считает формула раздела 11.5.1.

## Честные ограничения (что не реализовано или упрощено)

Раздел 24 ТЗ прямо требует не выдавать красивые страницы за готовый продукт. Ниже — то,
что реализовано в упрощённом виде, и почему.

1. **Нет исходных PDF/изображений планировок.** Архив не был приложен к заданию — только
   текст. `data/project_catalog.json` содержит области/комнаты/примечания, **буквально
   перенесённые из текста ТЗ**, а не заново распознанные из PDF. При первом реальном
   использовании 13 планировок нужно загрузить их through тот же обработчик
   `/api/uploads/pdf`, что и для новых домов — обработчик для этого готов и протестирован.
2. **Геометрический движок — не полный CAD.** Реализованы уровни 2–3 из раздела 7.5
   («по конструктивному шаблону» и «по аналогу»), а не уровень 1 («по рабочим чертежам»).
   Для 11 из 13 стартовых планировок (прямоугольный закрытый контур — `rectFootprint` в
   `project_catalog.json`) стены, кровля, утепление, наружная облицовка и плёнки А/АМ
   считаются **по реальной геометрии**: периметр × высота, минус вычтенные проёмы окон
   (раздел 11.5.1), площадь ската по формуле раздела 7.2 (`горизонтальная_проекция / cos(9°)`,
   сверено с примером «подъём конька ≈0,6335 м при пролёте 8 м»), объём утеплителя по
   толщине слоя — каждая строка с реальным количеством × реальной ценой за единицу
   (`shell.ts`, покрыт тестами `calc-engine/test/shell.test.ts` и
   `server/test/buildEstimate.test.ts`). Для двух планировок с составным/Г-образным
   контуром (Норма 38, Норма 54) движок честно этого не делает — площадь пола берётся из
   экспликации, а стены/кровля остаются `needs_size`, а не подменяются прямоугольником.
   Каркас, крепёж и работы по сборке (для которых нет ни чертежа, ни нормы на узел) во всех
   случаях остаются оценкой по аналогу от исторического Барна 96 (раздел 16.2, формула
   `H = H_аналога × новый/аналог × коэффициент`), всегда со статусом `preliminary_by_analog`.
   Для Норм высота стены (`clean_ceiling_height_mm`) остаётся `null`, пока владелец не
   подтвердит профиль (раздел 7.3) — движок в этом случае показывает конкретный пробел
   `wall_height_missing`, а не подставляет 2700/3000 мм.
3. **Импорт PDF реализует этапы 1–5 из раздела 20.1** (приём, извлечение векторного
   текста, классификация страниц, кандидаты на размеры) для PDF с текстовым слоем.
   Этапы 6–10 (топология полигонов, увязка листов, редактируемая накладка на плане) —
   честно НЕ реализованы: это отдельный геометрический редактор, требующий отдельного
   проекта. Сканы без текстового слоя (нужен OCR/визуальная модель) помечаются, но не
   обрабатываются — ключ внешнего OCR/vision-сервиса в этой среде не подключён; адаптер
   спроектирован так, чтобы такой сервис можно было добавить, не меняя остальной пайплайн.
4. **Раскрой** реализован как воспроизводимая эвристика (First-Fit-Decreasing с пропилом),
   явно не заявлен оптимальным — как и требует раздел 9. 2D-раскрой листов (ЛДСП/OSB)
   упрощён до нижней оценки (площадь/площадь листа), без полноценной карты раскладки.
5. **Назначение цеха на конкретные проекты** не реализовано отдельной таблицей — Цех
   технически видит список всех проектов (без коммерческих полей), а не только
   «назначенные». Ограничение отражено в комментарии кода (`projects.ts`) как известный
   пробел, а не скрыто.
6. **Электрика/сантехника/отопление** — справочные данные (`reference_tables.json`,
   `calculation_defaults.json`) перенесены из ТЗ полностью, но в живой расчёт сметы
   (`buildEstimate.ts`) сейчас включены как редактируемые опции с ручной ценой, а не как
   автоматический расчёт по точкам/трассам (раздел 13) — это отдельный по объёму модуль
   геометрии сетей, для которого в примере нет схемы конкретного нового дома.
   Формулы для этих разделов (тёплый пол, освещение, огранка кабеля) при этом полностью
   реализованы и протестированы в `calc-engine` — не хватает только автоматической
   геометрической привязки количества точек к конкретной новой планировке.
7. **Клиентская цена по блокам** — итоговая цена распределяется по коммерческим блокам
   пропорционально их доле в прямых затратах (`clientAllocation.ts`), а не через отдельно
   согласованную наценку на каждый блок (раздел 18 допускает оба варианта; текущий —
   самый прозрачный без дополнительного экрана настройки наценок по блокам).
8. **План/график работ цеха** — учёт факта (план/факт часов) реализован; календарное
   планирование с зависимостями этапов и параллельными бригадами (раздел 16) — нет.
9. **Демо-аккаунты** имеют предсказуемые пароли и помечены `isDemo: true` — обязательно
   сменить перед реальной эксплуатацией (раздел 3 требует отделять их от рабочих).

## Структура каталога и таблица приёмки

`data/project_catalog.json`, `data/window_catalog.json`, `data/calculation_defaults.json`,
`data/reference_tables.json` соответствуют файлам, описанным в приложении В1 ТЗ.
Контрольные площади всех 13 планировок (раздел 23.1) взяты один в один из приложения Г и
использованы как есть — они являются частью самого задания, а не отдельно проверенным
результатом распознавания.

Полный список пройденных числовых контрольных примеров раздела 23 — в тестах
`calc-engine/test/*.test.ts` (57 тестов) и `server/test/*.test.ts` (8 тестов, включая
проверку геометрии стен/кровли на реальном каталожном доме). Каждый тест называется в
терминах соответствующего пункта ТЗ, чтобы было видно прямое соответствие.
