# Luxury House — калькулятор модульных домов

Рабочая система расчёта модульных домов (Абакан) для трёх ролей — **Цех**,
**Менеджер**, **Владелец** — на одной расчётной модели. Реализовано по
мастер-промпту (`Luxury_House_Calculator_Master_Prompt_1.md`).

## Стек и почему

- **Next.js 14 (App Router) + TypeScript** — один процесс на фронтенд и
  бэкенд (API-роуты), серверная авторизация из коробки, не нужен отдельный
  API-сервис для MVP такого масштаба.
- **Prisma + SQLite** — файловая БД без внешней инфраструктуры для запуска
  «из коробки»; схема реляционная, миграция на Postgres — это только смена
  `provider`/`DATABASE_URL` в `prisma/schema.prisma`, код не меняется.
  SQLite не поддерживает enum на уровне БД — статусы/роли хранятся строкой
  и валидируются на уровне приложения (`src/lib/domain/enums.ts`).
- **NextAuth (Credentials + JWT)** — серверная сессия с ролью пользователя;
  роль никогда не приходит от клиента.
- **Decimal.js** — все денежные формулы считаются в `Decimal`, округление
  до копеек/шага явное (`src/lib/calc/money.ts`).
- **playwright-core (готовый headless Chromium из окружения) → PDF**,
  **docx → DOCX**, **exceljs → XLSX** — реальные, открываемые файлы.
  PDF через браузер, а не `pdf-lib`, потому что стандартные шрифты pdf-lib
  не содержат кириллицы; рендер через Chromium получает кириллицу,
  переносы строк и разрывы страниц бесплатно.
- **Vitest** — модульные и интеграционные тесты расчётного ядра.

## Архитектура

```
src/lib/calc/*         — чистое расчётное ядро, НЕ зависит от UI/БД.
                          money, units, cutting (раскрой), geometry, piles,
                          film, finishes (плитка/потолок), lighting,
                          floorHeating, labor, overhead, pricing, options.
                          Каждый модуль покрыт тестами на конкретные примеры
                          из §23 мастер-промпта (с ожидаемыми числами).

src/lib/domain/*        — доменный слой поверх ядра:
  enums.ts               роли/статусы (строки в БД + типы в приложении)
  snapshot.ts             тип EstimateSnapshot — единый «снимок» расчёта
  rbac.ts                 матрица прав §3 + redactSnapshotForRole()
  referenceData.ts        стартовые цены/нормы из Приложения А
  templates/               шаблоны домов (Барн 96/Кызыл, Норма 77) —
                            строят EstimateSnapshot через calc-ядро

prisma/schema.prisma     — User, Customer, Project, ProjectVariant,
                            EstimateRevision (неизменяемый снимок + версия),
                            Material, WorkNorm, PricingPolicy,
                            ActualWorkEntry, MaterialMovement (идемпотентны
                            по idempotencyKey), Approval, ExportSnapshot.

src/app/api/*             — API-роуты, каждый запрос проверяет роль через
                            requireRole()/permissions (§3: «проверяй права
                            для каждого API-запроса»).

src/app/{manager,shop,owner}/* — три отдельных представления одной модели.
src/lib/export/*          — генераторы PDF/DOCX/XLSX, знают о ролевых
                            ограничениях содержимого (§21).
```

Порядок расчёта (§22): геометрия/шаблон → опции (`options.ts`, ADD / REPLACE
/ REMOVE / REQUIRE / EXCLUDE, идемпотентно) → физические количества → сваи
(`piles.ts`) → раскрой (`cutting.ts`) → труд (`labor.ts`) → прямые затраты →
резерв/накладные (`overhead.ts`) → цена (`pricing.ts`, 3 режима) →
ролевое представление (`rbac.ts`) → экспорт.

## Запуск

```bash
npm install
cp .env.example .env            # при необходимости отредактировать
npx prisma migrate dev --name init
npm run prisma:seed             # создаёт демо-пользователей и справочники
npm run dev                     # http://localhost:3000
```

Демо-доступы (отдельно от рабочих данных, см. §3 — помечены `isDemo=true`):

| Роль     | Email                       | Пароль             |
|----------|------------------------------|---------------------|
| Владелец | owner@luxuryhouse.demo       | owner-demo-2026     |
| Менеджер | manager@luxuryhouse.demo     | manager-demo-2026   |
| Цех      | shop@luxuryhouse.demo        | shop-demo-2026       |

Тесты расчётного ядра:

```bash
npm test          # vitest run — 54 теста, покрывают §23 п.1-24
npm run typecheck
npm run build      # прод-сборка Next.js
```

## Что реально работает (проверено в этой сессии)

- Менеджер: выбор шаблона (Барн 96/Кызыл, Норма 77), опции (тёплый пол,
  конвекторы, плитка санузла, кочегарка), живой пересчёт цены через
  `/api/estimate/preview`, сохранение варианта, экспорт клиентского
  предложения (PDF и DOCX — реально открываются, проверено).
- Цех: список выпущенных заданий (видны только версии со статусом
  `PRODUCTION_TASK` и позже — «актуальная выпущенная версия», §4), ведомость
  без единой цены (проверено в PDF/XLSX и в JSON-ответе API), ввод
  фактических часов и движения материалов с идемпотентностью (повторный
  запрос с тем же ключом не создаёт вторую запись — проверено на прямую в
  БД).
- Владелец: полная себестоимость/резерв/накладные/прибыль по каждому
  проекту, внутренняя XLSX-смета, обзор бизнеса (KPI), просмотр
  представлений менеджера и цеха.
- RBAC проверен end-to-end через реальные HTTP-запросы (не только юнит-тест
  redactSnapshotForRole): менеджер получает 403 на `OWNER_XLSX` и
  `PRODUCTION_PDF`, цех получает 403 на `OWNER_XLSX`, JSON-ответ API не
  содержит числовых полей себестоимости/цены для запрещённой роли.
- Версионирование: «Пересчитать» создаёт новую строку `EstimateRevision`
  (version+1, `parentRevisionId`), исходная строка и её `snapshotJson` не
  меняются — проверено в БД после пересчёта.
- Расчётное ядро воспроизводит контрольный пример §Б1/тест #22 «в один
  клик»: с выключенными опциями цена сходится к 8 300 000 ₽, прибыль —
  2 102 353,32 ₽, себестоимость — 5 533 646,68 ₽ (см.
  `src/lib/domain/templates/barn96Kyzyl.test.ts`).

## Честные ограничения этой версии

Мастер-промпт описывает систему масштаба нескольких месяцев командной
работы. За одну сессию реализована работающая вертикаль (не заглушки), но
не 100% ширины каждого раздела. Явно не реализовано или упрощено:

1. **Геометрия.** Нет параметрического 3D-редактора стен/проёмов/крыш —
   `geometry.ts` и `piles.ts` реализуют формулы (L-образный контур, свайная
   сетка, сдвиг террасы, детализация) и покрыты тестами на числа из
   мастер-промпта, но в UI геометрия — это выбор готового шаблона
   (Барн 96/Кызыл, Норма 77), а не рисование произвольного дома. Ядро готово
   принимать более богатый ввод — не хватает редактора поверх него.
2. **Импорт чертежей/XLSX/PDF, OCR.** Не реализован. `resolveWallInstances()`
   в `geometry.ts` показывает принцип дедупликации листов/инстансов —
   реальный парсер загружаемых файлов не написан.
3. **Полная ведомость Барн 96.** Для контрольного примера (§Б1) прямые
   затраты сведены к сумме подтверждённых статей (сваи/крепёж/труд) плюс
   одна явно помеченная «предварительно по аналогу» строка-остаток —
   потому что полная построчная спецификация (`Barn_93_full_estimate.xlsx`)
   не была доступна в этой сессии. Итоговые деньги при этом *точно*
   совпадают с историческим примером (проверено тестом), но построчный
   BOM Барна не исчерпывающий. Норма 77 — ещё тоньше (см. её билдер).
4. **Электрика, водопровод, канализация, скважина, септик, крыльца,
   юбка, дымоход, кровельные доборы** — описаны в мастер-промпте
   формулами и нормами (раздел 13-15), но в расчётный движок как отдельные
   модули не перенесены. Их логика по духу такая же, как у `floorHeating.ts`
   (явные единицы, никаких скрытых удвоений) — следующий шаг: по модулю на
   раздел, с тестами на приведённые в промпте числа.
5. **Ценовые режимы/наценки по блокам и опциям** заданы на уровне всей
   сметы (3 формулы §18 реализованы и протестированы), но наценка
   по отдельным блокам/опциям — нет.
6. **Владелец: управление справочниками из интерфейса.** Справочник
   материалов/работ/политика цены — read-only экран
   (`/owner/settings`); редактирование — через `prisma/seed.ts` и БД.
   Права на изменение зашиты в модель (`Material.status`,
   `WorkNorm.hoursPerUnit: null` и т.д.), но формы редактирования не
   написаны.
7. **Назначение проекта конкретному работнику/бригаде цеха.** Видимость
   для роли «Цех» сейчас определяется статусом версии
   (`PRODUCTION_TASK+`), а не индивидуальным назначением — все работники
   видят все выпущенные задания. Модель это не блокирует (в
   `ActualWorkEntry` уже пишется `enteredByUserId`), просто UI назначения
   не сделан.
8. **Комиссия менеджера «только своя».** §3 разрешает менеджеру видеть
   размер только собственной комиссии по разрешению — сейчас комиссия
   вообще скрыта от менеджера (упрощение в сторону более строгого, а не
   более слабого, ограничения).
9. **Утверждения (Approval) скидки ниже границы** — API есть
   (`/api/revisions/[id]/approval`, только владелец), но UI-кнопки на
   странице менеджера для запроса такого утверждения нет.
10. **Экспорт-файлы не сохраняются повторно-скачиваемыми** — каждый запрос
    генерирует файл заново «на лету» (детерминированно, из того же
    снимка), в БД остаётся аудит-запись `ExportSnapshot`, но сам файл на
    диск не пишется (в эфемерном окружении сессии это осознанный выбор).
11. **`npm audit`** показывает уязвимости в транзитивных зависимостях
    (в основном Next.js 14.2.x advisories, связанные с Image
    Optimizer/Server Actions на самостоятельном хостинге, и dev-зависимости
    vitest/tsx). Перед продакшн-деплоем стоит запустить `npm audit` заново
    и рассмотреть обновление минорной линии Next.js.

## Приёмочные тесты §23

Реализованные пункты 1-24 (все, что формулируется как проверка чистой
функции расчётного ядра) покрыты тестами — 54 теста в 13 файлах, команда
`npm test`. Пункты 25-28 (версии, права, идемпотентность) проверены и
модульно (`rbac.test.ts`), и end-to-end через реальные HTTP-запросы к
поднятому серверу в ходе разработки (см. историю сессии) — не
автоматизированы как e2e-сьют (Playwright test runner не подключён к
проекту, хотя `playwright-core` уже используется для PDF) — это
естественный следующий шаг.
